# C++ package compilation

`compileTypeScriptPackageGraph` is the public regeneration boundary for target repositories. One request supplies every source with its source package and package root, a versioned package graph, exact module dependencies where discovery is not sufficient, one backend, and its options. The compiler lowers each source once and prepares graph-wide backend analysis once.

The graph schema is `flight-compiler-package-graph/1`. Package dependencies are explicit and are checked against every cross-package module edge. Relative sibling edges are resolved from the supplied module set; package exports can be supplied through `CompilerModuleResolutionPlan`. An importer-specific resolution edge takes precedence over a workspace-wide export edge with the same specifier.

Named imports through a barrel are traced to their declaration modules. When one request reaches several modules, the compiler records disjoint `importedNames` on the module-resolution and link-dependency edges, emits every required header, and keeps unrelated barrel sources out of the consumer's refusal closure. Side-effect, namespace, renamed, and re-export requests retain their whole-module dependency because they cannot be split without changing the public facade.

The result report uses `flight-compiler-package-report/1` and contains:

- one emitted or refused outcome per source module;
- stable refusal codes, stages, and lowering source locations;
- dependency-closed partial output, so no reported file depends on a refused module;
- source ownership and normalized dependencies for every emitted file;
- package dependency and output-file inventories; and
- the target-neutral ECMAScript module evaluation plan for the surviving entry closure.

The C++ backend accepts a `packageTargets` record. Namespace and installed include identity are separate, so `@flighthq/types` can emit under namespace `flight::types` and include prefix `flight/types` without rewriting generated text.

`externalBindings` uses `flight-cpp-external-bindings/1`. Each ambient type or value binding declares its required headers, qualified C++ target, type or value space, nullability, ownership, optional static members, and optional constructor or factory spelling. A value binding may also declare `callResultType`, the exact C++ type spelling that provides evidence for `ReturnType<typeof ambientValue>`; the field is invalid on type-space bindings, and an absent field does not authorize inference from the target spelling. This evidence does not model `Parameters<T>` or variadic/rest projections. Reachable ambient symbols without exactly one built-in or downstream binding are refused. Native binding manifests live with the target package or host adapter; the compiler does not import their implementation.

A shared, non-null type-space binding may declare `weakKeyPolicyTargetName`. For an exact ambient key `K`, this authorizes `flight::WeakMap<K, V, Policy>` with the declared qualified C++ policy as `Policy`; absence continues to refuse that external key. The policy is one cohesive ABI and must provide nested `weak_type` and `identity_type` types plus static `weaken(const K&) -> weak_type`, `lock(const weak_type&) -> std::optional<K>`, `identity(const K&) -> identity_type`, `hash(const identity_type&) -> std::size_t`, and `equal(const identity_type&, const identity_type&) -> bool` operations. `weak_type` and `identity_type` must not retain `K`; identity must remain stable for the source object's lifetime, equality must mean source object identity, hashes must agree for equal identities, and locking must fail after the last strong owner disappears. Flight-owned reference keys use `flight::WeakMap<K, V>` and its runtime default policy. A union key may use a custom policy only when every member declares the same policy; missing, mixed default/custom, or differing policies remain refusals. A policy field on a value-space, nullable, borrowed, owned, or value binding is malformed, and unrepresented values remain refused.

The flight-cpp profile gives the exact source type `WeakMap<object, unknown>` one narrower opaque-cache ABI: `flight::WeakMap<flight::Ref<void>, flight::ErasedValue>`. An immutable local assertion to `WeakMap<K, V>` may acquire `flight::checked_weak_map_view<K, V>` only when `K` is a compiler-proven Flight reference and `V` has a concrete representation. The view aliases the original map storage, erases `K` without changing source object identity, boxes writes with their exact emitted `V`, and checks that tag before returning a read. A mismatched read fails with `flight::BadErasedValueCast`; it never fabricates `V`. Mutable bindings, returned or passed assertions, non-object erased keys, external key policies, unions, and still-unknown view values remain refusals. This is the sole `unknown` container lane; it does not make `unknown` generally representable.

The initialization report plans dependency order, live bindings, declaration initialization, and supported executable top-level statements. C++ carries synchronous top-level control flow through ordered inline initialization closures. Top-level `await` remains a structured refusal until asynchronous module evaluation is represented, and nested `var` remains refused where preserving its module-scoped binding would require declaration hoisting.

The [flight-cpp adoption register](../agents/flight-cpp-adoption.md) tracks runtime headers, host manifests, ABI coordination, build integration, and downstream release gates required by the compiler's current emitted contract. It remains in this repository until `flight-cpp` adopts an equivalent maintained register.
